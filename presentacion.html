Editorial

Una pregunta
sencilla.

¿Y si hablar con una base de datos fuera tan fácil como preguntarle a un compañero?

Este proyecto explora esa idea con dos bases de datos muy distintas: las tablas de meteoritos de la NASA y los documentos anidados de Airbnb. LangChain actúa como pegamento; Ollama ejecuta modelos en local; Groq los ejecuta en la nube. La pregunta es la misma. La arquitectura cambia.

No buscamos que el modelo “sepa” la base de datos. Buscamos que aprenda a preguntarle: que lea el esquema, genere una consulta válida y explique el resultado con los datos delante.

El LLM no lee la base de datos: aprende a preguntarle.

01 · El reto

El problema no es la IA.
Es el contexto.

Un LLM no puede leer 5.555 documentos y 45.761 filas en cada pregunta. Y no debería.

La tentación es enorme: coger la base de datos, convertirla en texto y meterla en el prompt. El resultado sería caro, lento y frágil. La ventana de contexto se llena antes de que llegue la pregunta; cada token viaja, se procesa y se paga; y los datos dejan de estar bajo control.

La alternativa es más interesante: darle al modelo el mapa, no el territorio. El esquema, los tipos y unos pocos ejemplos. Con eso puede escribir una consulta que el motor de la base de datos ejecuta en milisegundos.

Un $match con $all, seguido de $sort, $project y $limit.

El mapa, no el territorio.

06 · El retoPBD / 2026

Las cuatro tensiones

Lo que se rompe al meterlo todo en el prompt.

01

Contexto

La ventana se llena antes de que llegue la pregunta. Los documentos largos desplazan la instrucción.

02

Coste

Cada token viaja, se procesa y se paga. Repetir la base de datos en cada consulta no escala.

03

Privacidad

Los datos no siempre pueden salir de casa. Enviar la base de datos a una API es una decisión, no un detalle.

04

Verdad

Sin datos delante, el modelo rellena huecos. La respuesta suena bien y puede ser falsa.

BD completa → promptdescartado
Esquema + pregunta → consultaelegido
Antes

La base de datos en el prompt

5.555 documentos y 45.761 filas viajando en cada pregunta. Contexto, coste y privacidad disparados.

Ahora

El esquema en el prompt

Campos, tipos y un ejemplo. El motor filtra y devuelve solo tres o cinco registros.

La solución no es meter más datos: es generar la consulta correcta y leer solo lo que hace falta.

02 · La herramienta

LangChain: el pegamento entre el lenguaje y los datos.

No es un modelo. Es una capa de orquestación que conecta prompts, modelos, herramientas y agentes.

En el proyecto aparece en dos formas. En la nube, como una cadena de dos pasos: generar la consulta y redactar la respuesta. En local, como un agente que decide qué herramienta usar, observa el resultado y vuelve a intentarlo si hace falta.

python · lcellangchain_core
from langchain_core.prompts import ChatPromptTemplate

prompt = ChatPromptTemplate.from_messages([
    ("system", "Traduce la pregunta a un pipeline."),
    ("human", "{pregunta}"),
])

chain = prompt | llm
respuesta = chain.invoke({"pregunta": pregunta})

03 · La decisión

¿Por qué LangChain y no el SDK de turno?

Porque el proyecto cambia de modelo, de base de datos y de estrategia. La capa de orquestación evita reescribir la fontanería.

01

Un modelo, muchos proveedores

ChatOllama y ChatGroq comparten interfaz. Cambiar de entorno es cambiar una línea.

02

Menos fontanería

Prompts, herramientas, agentes y streaming ya están resueltos y probados.

03

Metadatos y streaming

Tokens, tiempos y pasos intermedios sin inventar instrumentación.

04

Un lenguaje común

El mismo prompt | llm en local y en cloud. La arquitectura se parece.

01

Una interfaz

ChatOllama y ChatGroq se comportan igual en la cadena.

02

Baterías incluidas

Prompts, herramientas, agentes y streaming sin escribirlos desde cero.

03

Una pega

La capa es código ajeno: hay que leerla, actualizarla y depurarla.

La decisión no fue “usar IA”. Fue elegir dónde poner la complejidad.

04 · Arquitectura

Cómo accedemos a los datos.

El LLM nunca recibe la base de datos. Recibe el esquema, genera una consulta y lee solo el resultado.

01

Esquema

Campos, tipos, subdocumentos y unos pocos ejemplos. El mapa, no el territorio.

02

Consulta

El modelo traduce la pregunta a un aggregation pipeline de MongoDB o a SQL.

03

Motor

MongoDB Atlas o PostgreSQL ejecuta el filtrado y devuelve solo los registros relevantes.

04

Síntesis

Una segunda llamada redacta la respuesta en español con los datos delante.

python · schema groundinganti-alucinaciones

05 · Local

La IA que vive en tu portátil.

Ollama descarga y ejecuta modelos en tu máquina. Expone una API compatible con OpenAI y se integra con LangChain mediante ChatOllama.

Es la opción privada: el prompt, los datos y la respuesta no salen de casa. También es la opción barata: no hay tokens que pagar. El precio se paga en hardware, velocidad y calidad.

qwen3.5:4bgemma-4num_ctx = 8192keep_alive = 15m
python · ollamalangchain_ollama
from langchain_ollama import ChatOllama
from langchain.agents import create_agent

llm = ChatOllama(model="gemma-4", temperature=0)
agent = create_agent(model=llm, tools=tools, system_prompt=SYSTEM_PROMPT)
01

Instalación

Un demonio en la máquina y modelos descargados con ollama pull.

02

Modelos

qwen3.5:4b y gemma-4, con temperature = 0.

03

Contexto

num_ctx = 8192 y keep_alive = 15m para no recargar en cada pregunta.

El mismo agente sirve para SQL y NoSQL; solo cambian las herramientas.

06 · Cloud

Velocidad de vértigo, fuera de casa.

Groq ejecuta modelos abiertos en su hardware y los expone con una API compatible con OpenAI. Ideal para comparar modelos sin montar infraestructura.

La nube cambia el perfil de riesgo: los datos salen de la máquina, pero la latencia baja y la calidad sube. En este proyecto es la ruta que alimenta la demo de Streamlit.

07 · Relacional

Tablas, filas y un agente que sabe mirar.

45.761 meteoritos de la NASA convertidos en una tabla limpia de PostgreSQL.

El CSV original se limpia con pandas: se elimina la columna geográfica, se renombra la masa y se fuerza un entero que admite nulos. Después, SQLAlchemy crea la tabla con tipos explícitos.

namemass_gyearrecclassfallreclatreclong
python · cargapandas + sqlalchemy
df = pd.read_csv("Meteorite_Landings.csv")
df = df.drop(columns=["GeoLocation"])
df = df.rename(columns={"mass (g)": "mass_g"})
df["year"] = df["year"].astype("Int64")

df.to_sql("meteoritos", engine, if_exists="replace", index=False, dtype=tipos_sql)
01

Quitar ruido

Se descarta GeoLocation: está duplicado en latitud y longitud.

02

Nombres claros

mass (g) pasa a mass_g para que el modelo no adivine.

03

Tipos explícitos

year se fuerza a entero con nulos; el resto de campos se declara en SQLAlchemy.

El esquema se lee en vivo; no está escrito a mano.

08 · Documental

Documentos que se parecen a la realidad.

5.555 alojamientos de Airbnb con campos anidados, listas y tipos propios.

MongoDB no impone un esquema rígido. Eso es una ventaja para modelar alojamientos reales y un problema para un LLM que necesita saber qué campos existen. La solución: schema grounding.

json · documentosample_airbnb
{
  "name": "Sunny flat",
  "address": { "market": "Barcelona" },
  "amenities": ["Wifi", "Air conditioning"],
  "price": 120,
  "host": { "host_is_superhost": true }
}
Campo

address.market

La ciudad anidada. Filtrar por ella requiere conocer la ruta completa del campo.

Campo

amenities

Un array: la búsqueda usa $all para exigir varios servicios a la vez.

Campo

price

Llega como Decimal128; hay que convertirlo antes de devolverlo como JSON.

Campo

host.host_is_superhost

Un booleano dentro de un subdocumento: otro ejemplo de por qué hace falta el esquema.

El esquema se describe; los documentos no se envían.

El pipeline

Una tubería, no una frase.

json · aggregationtext-to-mql
[
  { "$match": {
      "address.market": "Barcelona",
      "amenities": { "$all": ["Wifi", "Air conditioning"] }
  }},
  { "$sort": { "price": 1 } },
  { "$project": { "_id": 0, "name": 1, "price": 1 } },
  { "$limit": 5 }
]
Por qué

Pipeline y no find

Filtros, orden, proyección y límite en una sola estructura JSON.

Cuidado

BSON → JSON

Los precios llegan como Decimal128; hay que serializarlos con json_util.

01

Filtrar primero

$match reduce los documentos antes de ordenarlos o proyectarlos.

02

Proyectar después

$project elimina reseñas e imágenes que no caben en el contexto.

03

Limitar siempre

$limit convierte una respuesta enorme en cinco resultados legibles.

El prompt pide $project y $limit. Sin ellos, un documento de Airbnb puede arrastrar reseñas e imágenes hasta agotar el contexto.
